# End-to-end test — v0.1 against real WhatsApp (2026-11-10)

First test of the v0.1 skeleton against WhatsApp, on a Linux server with Docker
(`docker compose`, PostgreSQL 17), one instance linked to a real personal number.
A small receiver on the same Docker network checked every webhook's signature and logged
only metadata (event, type, masked sender) — never message content.

## Results

| Area | Result |
|---|---|
| Build (`golang:1.27-alpine` → distroless) | OK — 32 MB image |
| Startup, `/health`, admin key | OK — 401 without/with wrong key, 200 with the admin key |
| Create instance | OK — API key shown once |
| Link with **pairing code** | OK — code accepted on the phone, `status=connected`, history sync ran |
| Send text | OK — WhatsApp message id returned in ~300–400 ms |
| Receive (`message.received`) | OK — text, image, audio, sticker, reaction; group chats, the owner's own reply (`fromMe`) and a **private message from a third party** |
| Connection events (`connection.update`) | OK — emitted on reconnect |
| Status (`message.status`) | OK — read receipts |
| Webhook signature (`X-FireZAP-Signature`) | OK — 29/29 valid, 0 invalid |
| Restart → session restored | OK — reconnected by itself in ~4 s, no new pairing |
| Auth isolation | OK — instance key cannot use admin routes or another instance (401) |
| Input validation | OK — empty text, bad recipient, broken JSON, 2 MB body, bad instance id → 400 with clear messages |

## Findings (to fix before production use)

1. **`PUT /instances/{id}/webhook` echoes the webhook `secret` in clear text** in its response.
   It should be masked, as `GET /instances/{id}` already does, so the secret does not end up in
   proxy, terminal or integration logs.
2. **Duplicate `message.received` events.** For 5 messages the same message id was delivered
   twice: once as `type=other` and once with the real type (`text`, `reaction`). Integrations
   would show the message twice. Likely a protocol/side message (e.g. sender-key distribution)
   being emitted as its own event — skip events with no user-visible content, or merge them.
3. **Senders and chats arrive as LIDs, not phone numbers.** 14 events (including the owner's own
   reply and the private message from a third party — the real customer-service case) had `sender`/`chat` as `…@lid` identifiers. Integrations that key
   conversations by phone number cannot match them. whatsmeow keeps the LID ↔ phone mapping;
   the event should also carry the phone-number JID (e.g. `senderPn`, `chatPn`) when known.
4. **Webhook URL accepts internal addresses** (`http://169.254.169.254/…` was accepted).
   When the API is offered to third parties this is an SSRF vector into the host network.
   Block loopback, link-local (including cloud metadata) and private ranges by default — checked
   after DNS resolution and on every delivery — with an explicit opt-in setting for
   single-tenant setups that deliver to other containers on the same Docker network.

## Expected gaps of v0.1 (not bugs)

- Media is reported only as a `type`; there is no download URL or media send yet.
- No web dashboard yet (the README lists it as planned).

## Not yet tested

- Long-running stability (hours/days), reconnection after network loss, logout from the phone.
